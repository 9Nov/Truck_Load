# TMMA Loading Channel Scheduler

Streamlit app ที่จัดคิวรถบรรทุก (LORRY) เข้ารับสินค้าเคมีภัณฑ์ที่ช่องโหลด **A / B / C**
จากรายการ DO ของแต่ละวัน ด้วย **time-indexed MILP** (5 นาที/slot) แก้ด้วย HiGHS solver
ที่มากับ `scipy.optimize.milp` — ไม่ต้องติดตั้ง solver ภายนอก

## ติดตั้ง

```bash
pip install -r requirements.txt
```

ต้องใช้ Python 3.11 ขึ้นไป

## รัน

```bash
streamlit run app.py
```

เปิดเบราว์เซอร์ที่ http://localhost:8501

## ข้อมูลเข้าระบบ (production)

แอปตัวนี้**ไม่มีข้อมูลตัวอย่างในตัว** — ทางเข้าข้อมูลมีสองทางเท่านั้น

1. **อัปโหลดไฟล์ DO** (.xlsx / .xls / .csv) ในขั้น 1 ของหน้าวางแผนต้นวัน ·
   กล่องอัปโหลดจะเปิดเองเมื่อยังไม่มีข้อมูล · มีปุ่มดาวน์โหลด template ให้ในกล่องเดียวกัน
2. **พิมพ์เองในตาราง** ด้วยปุ่ม ➕ เพิ่มแถว (สำหรับแก้/เพิ่มรายบรรทัด)

พิกัด GPS ของรถในโหมดปรับแผนระหว่างวันก็เช่นกัน — อัปโหลดจากไฟล์ที่มีคอลัมน์
`DO No.` / `Lat` / `Lon` / `Last seen` หรือพิมพ์ในตารางโดยตรง

> ตัวสร้างข้อมูลจำลองย้ายไปอยู่ที่ `tests/sample_data.py` ซึ่งชุดทดสอบเรียกใช้เท่านั้น

## หน้าตา / UX

หน้าจอใช้ภาษาออกแบบเดียวกับ **F7/F8 Truck Slot Board** เพื่อให้เครื่องมือทั้งสองอ่านเป็นระบบเดียวกัน

- **Hero bar** บนสุดของทุกหน้า — ชื่อกระดาน, เวลาที่เป็นหลักของหน้านั้น (ช่วงเวลาทำงาน / เวลาปัจจุบัน)
  ตัวใหญ่แบบ mono และ **แถบสถานะหนึ่งบรรทัด** ที่สรุปว่าตอนนี้สถานการณ์โอเคไหม (เขียว/เหลือง/แดง พร้อมจุดสี)
- **Card + pill header** — ทุกส่วนเป็นการ์ดขาวบนพื้นเทา หัวการ์ดมีป้ายลำดับขั้น (ขั้น 1 / 2 / 3) และ
  **หัวข้อที่เขียนเป็นคำถามที่ส่วนนั้นตอบ** เช่น "วันนี้มีรถต้องเข้ากี่คัน", "รถที่ยังไม่เข้า ตอนนี้อยู่ไหน",
  "แผนใหม่ต่างจากเดิมตรงไหน" แทนชื่อฟีเจอร์
- **ตัวเลขสรุปแบบ tile** แทน metric เดิม — ตัวเลขใหญ่ mono + คำอธิบาย + บรรทัดเล็กบอกความหมาย
  และ **ใส่สีตามความหมาย** (เขียว = ดี, เหลือง = ต้องดู, แดงเส้นประ = หลุดแผน, เทา = ข้อมูลเฉย ๆ)
- **สีสื่อความหมายด้วยขอบ 2px + พื้นอ่อน ไม่ใช่สีตัวอักษรอย่างเดียว** เพื่อให้ยังอ่านออกเมื่อพิมพ์ขาวดำ
  หรือผู้ใช้ตาบอดสี
- **ตัวเลขทุกตัวเป็น tabular mono** (IBM Plex Mono) เวลาและจำนวนจึงเรียงตรงคอลัมน์กันเสมอ

### กระดานคิว — 2 มุมมอง

**🗓️ ปฏิทินรายช่อง (ค่าเริ่มต้น)** — คอลัมน์ = ช่องโหลด, แนวตั้ง = เวลา เหมือน day view ของปฏิทิน
อ่านง่ายกว่าตอนใช้งานหน้างาน เพราะ "ช่อง B ตอน 14:00 ทำอะไรอยู่" ดูจุดเดียวจบ ไม่ต้องไล่สายตาตามแท่ง

- **หัวคอลัมน์** บอกว่าช่องนี้รับสินค้าอะไรได้บ้าง (chip สีตาม product) · ใช้ช่องไปกี่ % ·
  ตอนนี้ว่างหรือไม่ว่างถึงกี่โมง · กี่เที่ยว และมีช่องว่างระหว่างคิวรวมกี่นาที
- **การ์ดรถแต่ละคัน** 3 บรรทัด: เวลา–เวลา + สินค้า / ผู้ขนส่ง / DO No. · นาที · เวลาที่เผื่อ
  ขอบซ้ายเป็นสีของ product
- **สถานะสื่อด้วยกรอบ + ป้ายมุมขวา** — ฟ้า `กำลังโหลด` · เขียว `รถรออยู่` · แดง `ถึง HH:MM` (จะมาสาย) ·
  เทา `ถึง HH:MM` · เส้นประ `ไม่รู้ตำแหน่ง` · จางลง + ✓ `เสร็จแล้ว`
- **ช่องว่างที่เสียไป** วาดเป็นกล่องลายทางแดง `ว่าง N น.` (เฉพาะที่เกิน 30 นาที และไม่ใช่ช่วงพัก)
  เวลาที่เสียจึงเห็นเป็นรูปธรรม ไม่ใช่แค่ที่ว่างเปล่า ๆ
- **เส้นแดงนอน** = เวลาปัจจุบัน · **แถบเทา** = ช่วงพัก · **แถบลายทางเทา** = ช่องปิดซ่อม ·
  หัวคอลัมน์ sticky ตอนเลื่อนดู
- ปรับความสูงต่อชั่วโมงได้ (44 / 62 / 84 / 112 px)

**📊 Timeline แนวนอน** — มุมมอง Plotly เดิม เหมาะกับการดูภาพรวมทั้งวันในจอเดียว
และมีเลนกล้อง/ตาชั่งให้เห็น bottleneck

> กระดานนี้มีเฉพาะช่อง **A / B / C** — ช่อง D เป็นของ Truck Drum / Dry container ซึ่งอยู่นอกขอบเขตของระบบนี้

สีของ product ยังจัดกลุ่มตาม family ตามกติกาเดิม (MAA แดง/ส้ม · MMA ม่วง · i-BMA ฟ้า · n-BMA เขียว)
เปลี่ยนเฉพาะเฉดให้เข้าชุดกับกระดาน — ถ้าต้องการให้ตรงกับ F7/F8 เป๊ะ (MMA เขียว · nBMA เหลือง)
แก้ที่ `PRODUCT_COLORS` ใน `ui_theme.py` ที่เดียว

## วิธีใช้

1. **Settings (sidebar)** — วันที่วางแผน / เวลาเริ่มโหลด / เวลาที่คันสุดท้ายต้องเสร็จ / ช่วงพัก 2 ช่วง /
   **ช่วงปิดช่องซ่อมบำรุง (ข้ามวันได้)** / เวลาที่ใช้กล้อง+ตาชั่งจริงต่อรอบ Weight-In / Weight-Out
   ค่าทั้งหมดถูกส่งเข้า solver โดยตรง ไม่มี hard-code ใน engine
   · **เวลาเผื่อ (Buffer) ไม่ได้อยู่ที่นี่** — อยู่ในคอลัมน์ `Buffer (นาที)` ของหน้า ⚙️ เวลามาตรฐาน
   เพราะต้องตั้งต่างกันรายแถว
2. **ตาราง DO** — **อัปโหลด Excel/CSV ของวันนั้น** (แทนที่หรือเพิ่มต่อท้ายก็ได้ ระบบอ่านหัวคอลัมน์
   แบบยืดหยุ่น เช่น `DO`, `Volume`, `Requested`) แล้วแก้เพิ่มเติมในตารางได้ · จะพิมพ์เองทั้งหมด
   ด้วยปุ่ม ➕ เพิ่มแถว ก็ได้
   - ในกล่องอัปโหลดมีปุ่มดาวน์โหลด **Excel template** — sheet แรกชื่อ `DO List` ว่างพร้อม dropdown
     ของ Product / Transport Co. และ validation ของ Volume / Margin, อีก 2 sheet เป็นตัวอย่างและคู่มือ
     (แอปอ่านเฉพาะ sheet แรกเท่านั้น)
   - `Requested Time` เว้นว่าง = ยืดหยุ่น ระบบเลือกเวลาให้
   - `Requested Time` มีค่า = **hard deadline** ต้องโหลดเวลานั้นเป๊ะ
   - `Transport Co.` = **Yusen** → ใช้ standard ISO Tank (ไม่ขึ้นกับน้ำหนัก, Buffer = 0) ·
     บริษัทอื่น → ใช้ตาราง LORRY เดิม
   - `Margin (min)` = เวลาเผื่อเฉพาะ DO นั้น บวกต่อจาก Buffer ของแถวนั้น (บวกให้ทั้งสองตาราง)
3. **Run Scheduler** — LORRY ล้วน ~15 วินาทีสำหรับ 26 DO · **วันที่มี Yusen เยอะจะนานขึ้นมาก**
   (ตัวอย่าง 26 DO ที่มี Yusen 13 คัน ใช้ ~130 วินาที) เพราะ cycle 100–110 นาทีทำให้ช่องโหลดแน่นถึง ~91%
   การพิสูจน์ optimality จึงยากขึ้น — Time limit เริ่มต้นจึงตั้งไว้ 300 วินาที และถ้าชนเพดาน ระบบจะขึ้น
   คำเตือนว่าแผนที่ได้ยังใช้ได้จริงแต่ยังพิสูจน์ไม่ได้ว่าดีที่สุด
4. **ผลลัพธ์** — Gantt (interactive), ตารางผลลัพธ์, utilisation ของแต่ละช่อง,
   รายการ DO ที่จัดไม่ได้, และปุ่มดาวน์โหลด Excel (5 sheet — มี **Standard times** ที่บอกว่าแผนนี้
   คิดด้วยตัวเลขและ buffer อะไรรายแถว จึงย้อนกลับมาทำซ้ำได้จากไฟล์เดียว)

## โหมด 🔄 ปรับแผนระหว่างวัน (rolling-horizon re-optimization)

แผนที่ได้ตอนเช้าคือ **1st draft** ระหว่างวันรถมักมาไม่ตรงเวลา โหมดนี้แก้แผนใหม่จากสถานะจริง
โดยไม่ทิ้งสิ่งที่เกิดไปแล้วและไม่รื้อแผนทั้งกระดานโดยไม่จำเป็น

**หลักการ — แก้ MILP ตัวเดิม ไม่ได้เขียน algorithm ใหม่** เพิ่ม input ต่อ DO แค่ 3 ตัว

| input | ความหมาย | มาจากไหน |
|---|---|---|
| `locked_channel` + `locked_start` | คิวนี้เกิดไปแล้ว/กำลังเกิด → ตรึงไว้ที่เดิมเป๊ะ แต่ยัง**กินช่องโหลดและตาชั่งเหมือนเดิม** | สถานะ `กำลังโหลด` / `เสร็จแล้ว` (+ เวลาเริ่มจริงถ้าไม่ตรงแผน) |
| `earliest` (release time) | เวลาที่เร็วที่สุดที่รถคันนี้เริ่ม weigh-in ได้ — solver ห้ามจัดคิวก่อนเวลานี้เด็ดขาด | ETA จากพิกัด GPS (หรือพิมพ์ทับเองถ้าโทรถามคนขับแล้ว) |
| `now_min` | เวลาปัจจุบัน — ไม่มีคิวไหนถูกจัดย้อนอดีต | ตั้งใน UI |

**GPS → ETA** (`gps_eta.py`, ปรับได้ทุกค่าใน sidebar): ระยะเส้นตรงแบบ haversine × detour factor
÷ ความเร็วเฉลี่ยบนถนน + เวลาเผื่อหน้าประตู แล้ว**ปัดขึ้น**เป็นช่อง 5 นาที (ปัดขึ้นเสมอ เพื่อไม่ให้แผนมองโลกในแง่ดีเกินจริง)
รถที่อยู่ในรัศมี 1 กม. ถือว่า "จอดรออยู่แล้ว" → ETA = เดี๋ยวนี้
รถที่ไม่มีสัญญาณ GPS → ไม่มี release time ระบบถือว่าพร้อมตั้งแต่ตอนนี้ (และแจ้งว่าสัญญาณเก่ากี่นาทีแล้ว)

**"รถคันไหนเสียบคิวแทนได้"** ไม่ได้ใช้ heuristic แยก — release time ทำให้ MILP ตอบเองโดยอัตโนมัติ
รถที่ ETA ถึงก่อนคือรถที่มีสิทธิ์ลงช่องว่างนั้น และ solver จะเลือกชุดที่ดีที่สุดทั้งวันพร้อมกัน
ไม่ใช่เลือกทีละคันแบบ first-come-first-served (หน้าจอมีตาราง "รถแต่ละคัน" เรียงตาม ETA ให้ดูประกอบด้วย)

**Objective ตอน re-plan** — phase 1 เหมือนเดิม (maximize จำนวน DO ที่จัดได้) ส่วน phase 2 เพิ่มโทษความปั่นป่วน
แบบ **ไม่สมมาตร** เพราะสองทิศทางมีต้นทุนไม่เท่ากัน

| การเปลี่ยน | โทษ (ปรับได้) | เหตุผล |
|---|---|---|
| ย้ายช่องโหลด | 200 | คนขับถูกแจ้งช่องไปแล้ว ต้องสื่อสารใหม่ |
| เลื่อนออกไปช้าลง | 8 ต่อ 5 นาที | ผิดนัดที่แจ้งไว้ |
| **ดึงเข้ามาเร็วขึ้น** | **0** | รถที่ถูกดึงเข้ามาคือรถที่ ETA ยืนยันแล้วว่าถึงทัน — เป็นการอุดช่องว่างที่รถสายทิ้งไว้ ควรทำฟรี |

โทษพวกนี้ **ไม่กระทบจำนวน DO ที่จัดได้** (ถูกล็อกไว้ตั้งแต่ phase 1) กระทบแค่ว่าในบรรดาคำตอบที่ดีเท่ากัน จะเลือกอันไหน

**หน้าจอบอกอะไรบ้าง**: Gantt มีเส้นเวลาปัจจุบัน + แถบที่แช่แข็งไว้ (▪) · แท็บ "สิ่งที่เปลี่ยนไป" บอกทีละ DO ว่า
ย้ายช่อง / เลื่อนออก / เลื่อนเข้า / เพิ่มเข้าแผน / หลุดจากแผน พร้อมจำนวนนาที · แท็บ "รถแต่ละคัน" บอกระยะทาง ETA
และช้ากว่าแผนกี่นาที · DO ที่ล็อกเวลาไว้แล้วรถมาไม่ทันจะถูกแจ้งด้วยเหตุผลตรง ๆ ว่า *"รถถึงเร็วสุด HH:MM แต่ถูกล็อกเวลาไว้ที่ HH:MM"*
ไม่ใช่เลื่อนให้เงียบ ๆ

**ข้อจำกัดที่ควรรู้**
- **พิกัดโรงงานจริงไม่อยู่ในซอร์สโค้ด** — ค่าเริ่มต้นที่ ship มาเป็นแค่จุดคร่าว ๆ
  (`PLACEHOLDER_PLANT_LATLON` ใน `gps_eta.py`) ค่าจริงตั้งผ่าน **Streamlit secrets** แทน:
  คัดลอก `.streamlit/secrets.toml.example` ไปเป็น `.streamlit/secrets.toml` (ถูก gitignore ไว้แล้ว)
  แล้วใส่พิกัดจริง — ตอนใช้งานจริงแอปจะอ่านมาตั้งเป็นค่าเริ่มต้นให้เองที่ sidebar → 🛰️ GPS / ETA
  (แก้ทับในหน้าเว็บได้เสมอ) ถ้ายังไม่ตั้ง secrets และมีข้อมูล GPS เข้ามา แอปจะขึ้น error สีแดงเตือนว่า
  ETA ยังเชื่อถือไม่ได้ · บน Streamlit Community Cloud ตั้งค่าเดียวกันนี้ได้ที่ app **Settings → Secrets**
- ETA เป็นแบบเส้นตรง × factor ไม่ได้ดูสภาพจราจรจริง ถ้าจะต่อ routing API ให้แทนที่ `gps_eta.eta_for()`
  อย่างเดียว ส่วนที่เหลือไม่ต้องแก้ (solver รู้จักแค่ `earliest`)
- รถที่ไม่มีข้อมูล GPS ระบบถือว่าพร้อมทันที — ถ้าไม่จริงต้องใส่ ETA override เอง

### รถมาไม่ทัน — Auto หรือ Manual

ในขั้น 3 ของโหมดปรับแผนระหว่างวัน เลือกได้ 2 แบบ

**⚡ Auto** (เหมือนเดิม) — solver ดันคันที่สายออกไปตาม ETA และดึงคันที่พร้อมแล้วเข้ามาอุดช่องว่างเอง
เหมาะกับตอนที่เชื่อ ETA และอยากได้คำตอบเร็ว

**🙋 Manual** — ระบบเสนอ ผู้วางแผนเคาะ

1. แสดงรถที่ยังไม่เข้าทุกคันพร้อมคำตัดสิน: `ตรงเวลา / มาก่อน` · `สายเล็กน้อย` · `จะสาย N นาที — เกินเกณฑ์` · `ไม่มีสัญญาณ`
2. เฉพาะคันที่สายเกินเกณฑ์จะมีปุ่ม **วิเคราะห์รถทดแทน** เปิดดูคันที่เข้าแทนได้
3. คันแทนต้องผ่าน 3 เงื่อนไข — ลงช่องนั้นได้ตาม eligibility · รู้ตำแหน่ง · พร้อมเข้าก่อนคิวเดิมอย่างน้อย
   `lead_min` นาที โดยคันที่ยังอยู่บนถนนต้องบวกเวลาแจ้งคนขับ `notice_min` (คันที่จอดรออยู่หน้าโรงงานแล้วเรียกเข้าได้ทันที)
4. แต่ละตัวเลือกบอก trade-off ตรง ๆ: `ดึงเข้ามาเร็วขึ้น N นาที` (ดี) หรือ `คันนี้จะถูกเลื่อนออก N นาที` (แย่กว่า — เรียงไว้ท้าย)
   พร้อมบรรทัดสรุปว่าเป็นการสลับสินค้าในช่องหรือไม่ และพร้อมก่อนคิวกี่นาที
5. กด **เลือกคันนี้แทน** → เก็บเป็นรายการตัดสินใจ (ยกเลิกได้) · หรือ **ปิด ไม่สลับ** เพื่อปล่อยให้สายตามเดิม
6. กด **จัดคิวใหม่จากเวลานี้** ครั้งเดียว — การตัดสินใจทุกอันถูกแปลงเป็น `pin_channel` + เวลาที่ล็อก
   ส่งเข้า MILP ตัวเดิม แล้วคิวที่เหลือทั้งวันถูกจัดใหม่รอบเดียว

> **จุดสำคัญของการออกแบบ**: การกดเลือกไม่ได้สลับแถวใน UI แต่กลายเป็น**ข้อจำกัดที่ส่งเข้า solver**
> แผนที่ได้จึงยังผ่าน hard constraint ทุกข้อและ self-check เดิม ถ้าการตัดสินใจนั้นเป็นไปไม่ได้จริง
> (เช่นล็อกสินค้าลงช่องที่ลงไม่ได้ หรือเวลาที่เลือกไปคร่อมช่วงพัก) ระบบจะ**ปฏิเสธพร้อมบอกเหตุผล**
> ไม่ใช่เลื่อนให้เงียบ ๆ

คันที่ถูกแทนจะไปอยู่ตรงไหน เลือกได้ 2 นโยบาย: **เสียบกลับตามเวลาที่รถถึงจริง** (แนะนำ — ใช้ ETA เป็น release time)
หรือ **ต่อท้ายคิวของช่องนั้น** (กติกาเดิม ไว้กดเทียบ)

บางวันช่องโหลดต้องหยุดซ่อม และบางครั้งหยุดยาวหลายวัน — เพิ่มได้ที่ **sidebar → ⛔ ช่วงปิดช่อง (ซ่อมบำรุง)**

| ช่อง | ปิดตั้งแต่วันที่ + เวลา | เปิดอีกครั้งวันที่ + เวลา | เหตุผล |
|---|---|---|---|
| B | 12/09/2026 22:00 | 14/09/2026 16:00 | overhaul ปั๊ม |

รายการที่เพิ่มแล้วจะแสดงเป็นรายการใต้ฟอร์ม พร้อมปุ่ม ✕ ลบทีละรายการ ·
รายการที่**ไม่ตรงกับวันที่วางแผน**จะแสดงจาง ๆ พร้อมหมายเหตุ ไม่ถูกนำมาใช้กับแผนวันนั้น

### หยุดข้ามวันทำงานยังไง

sidebar มีช่อง **"วันที่วางแผน"** เพิ่มเข้ามา ระบบใช้วันนี้ตัดสินว่าช่วงซ่อมแต่ละรายการ
มีผลกับแผนวันนั้นช่วงเวลาไหน — ตัวอย่างช่วงซ่อม `B · 12/09 22:00 → 14/09 16:00`

|---|---|

| 14/09 | เปิดวัน – 16:00 |
| 15/09 | ไม่ปิด (จบแล้ว) |

### ต่างจากช่วงพักตรงไหน

ช่วงพักหยุดพร้อมกันทุกช่อง ส่วนช่วงปิดช่องกระทบแค่ช่องนั้น อีก 2 ช่องยังรับรถตามปกติตลอดช่วงเวลาเดียวกัน

### ระบบทำอะไรให้บ้าง

- เป็น **hard constraint** ระดับเดียวกับช่วงพัก — เวลาเริ่มที่เป็นไปได้ถูกคำนวณ**แยกรายช่อง**
  solver จึงไม่วางคิวคร่อมช่วงที่ปิดเลย (เวลาถูกปัดออกด้านนอกทั้งสองฝั่ง ไม่มีทางมองโลกในแง่ดีว่าช่องกลับมาเปิดเร็วกว่าจริง)
- **utilisation วัดจากเวลาที่ช่องเปิดจริง** มีคอลัมน์ `Closed (min)` เพิ่มในตารางสรุป
  ช่องที่ปิดครึ่งวันจึงไม่ถูกรายงานว่าขี้เกียจ
- **กระดานปฏิทิน** วาดแถบลายทางเทาทับเฉพาะเลนที่ปิด พร้อมป้าย `⛔ ปิดช่อง N น.` และเหตุผล ·
  หัวคอลัมน์บอกว่าวันนี้ช่องนี้ปิดไปกี่นาที · มุมมอง Timeline วาดเป็นแท่งเทาในเลนนั้น ·
  hero bar และ sidebar สรุปให้ด้วยว่าวันนี้ปิดช่องไหนกี่นาที
- **DO ที่ล็อกเวลาไว้ตรงกับช่วงปิด** จะถูกปฏิเสธพร้อมเหตุผล ไม่เลื่อนให้เงียบ ๆ ·
  ถ้าปิดทุกช่องที่สินค้านั้นลงได้ DO จะถูกแจ้งว่า *"ช่อง C ปิดซ่อมทับช่วงที่ลงคิวนี้ได้"*
- **รถที่กำลังโหลดอยู่ตอนช่องถูกปิด** ถือเป็นความจริงหน้างาน ไม่ถูกนับเป็นการละเมิดกติกา
  มีแต่คิวใหม่เท่านั้นที่ถูกห้าม
- ช่องว่างในกระดานที่จริง ๆ แล้วเป็นช่วงซ่อม จะไม่ถูกนับเป็น "ว่างเสียเปล่า"
- ช่วงที่ปิดติดไปกับไฟล์ Excel ที่ export ด้วย (sheet Settings)

## ⚙️ เวลามาตรฐานที่ใช้วางแผน (แก้ได้จากหน้าจอ)

โหมด **⚙️ เวลามาตรฐาน** ใน sidebar เปิดตารางเวลามาตรฐาน 2 ชุดให้แก้ได้โดยไม่ต้องแตะโค้ด
ค่าที่แก้มีผลกับการจัดคิวทันที (เก็บใน session ของเบราว์เซอร์นั้น)

### ค่าเริ่มต้นคือเวลาจริง ไม่ใช่ standard

ค่าเริ่มต้นทุกแถวคือ **P75 ของเวลาที่รถใช้จริง** (Lorry 3,601 เที่ยว · Yusen 1,213 เที่ยว · 12 เดือนล่าสุด)
ปัดเป็นจำนวนเท่าของ 5 นาที · มีเพียง **2 แถว** ที่ยังใช้ standard เดิมเพราะไม่มีเที่ยวจริงเลย (n=0)
คือ **MAA1-2 และ MAA3 ที่ 22-24MT**

**ทำไมใช้ P75 ไม่ใช่ค่ากลาง** — โมเดล MILP เป็น deterministic (หนึ่ง DO = เวลาค่าเดียว ไม่จำลองความแปรปรวน)
และวางคิวชิดกัน ตัวเลขที่ใส่เข้าไปจึงเท่ากับ *โอกาสที่จะไม่ล้นไปทับคิวถัดไป* โดยตรง ถ้าใช้ค่ากลางจะมีโอกาสราว 50%
ที่เที่ยวจริงนานกว่าที่จัดไว้แล้วดันคิวถัดไปช้าตาม ส่วน P75 เหลือความเสี่ยงราว 25% ซึ่งเป็นระดับเดียวกับที่
standard ของ Yusen ตั้งไว้อยู่แล้ว

**Buffer ต่อแถว — ที่เดียวที่ตั้งเวลาเผื่อได้** เพราะ P75 มีเวลาเผื่ออยู่ในตัวแล้ว แถวที่มาจากข้อมูลจริงจึงตั้ง
**Buffer = 0** ส่วน 2 แถวที่ยังใช้ standard เดิมตั้ง **Buffer = 10**

เดิม sidebar มีช่อง *Realistic Buffer* อีก 2 ช่อง (LORRY / Yusen) แต่ทุกแถวในตารางนี้มี buffer ของตัวเอง
และ `job_total_slots()` ให้ buffer ของแถวชนะเสมอ ค่าใน sidebar จึง**ไม่เคยถูกใช้เลยในเส้นทาง UI**
(รวมถึงตอนกด "กลับไปใช้ Standard เดิม" ซึ่งเขียน buffer 10 ลงในแถวตรง ๆ) — ช่องทั้งสองถูกถอดออกแล้ว
เพื่อไม่ให้เข้าใจผิดว่าปรับแล้วแผนจะเปลี่ยน · ฟิลด์ `realistic_buffer_min` / `yusen_buffer_min` ยังอยู่ใน
`SchedulerConfig` ในฐานะ fallback สำหรับการเรียก engine ตรง ๆ (test / batch script) ที่ส่ง entry ซึ่ง
`buffer_min = None` มา

> **ผลกระทบที่ต้องรู้**: ค่าจริงช้ากว่า standard เดิมมาก (เช่น MMA2 14MT จาก 50 → 75 นาที) วันหนึ่งจึงจัดรถได้
> **น้อยลงอย่างมีนัยสำคัญ** — ในการทดสอบชุดหนึ่ง 30 DO จัดได้ 26 คันด้วย standard เดิม แต่ 19 คันด้วยค่า P75
> นี่คือความจริงที่ standard เดิมบังไว้ ไม่ใช่ความสามารถที่หายไป

### ปุ่มในหน้านี้

- **↺ รีเซ็ตเป็นค่าเริ่มต้น** — กลับไปที่ P75 ของข้อมูลจริง (**ไม่ใช่** standard เดิม) รวม buffer ต่อแถว
- **⏮ กลับไปใช้ Standard เดิม** — ใช้ตาราง ISO มาตรฐานทั้งหมด พร้อม buffer 10 (LORRY) / 0 (Yusen) เหมือนแอปเวอร์ชันก่อน
- **⬇️ JSON / CSV** — สำรองค่าที่ปรับไว้ หรือส่งต่อให้คนอื่น

### กติกาตอนแก้ค่า

- ต้องเป็นจำนวนเท่าของ 5 นาที — ถ้าไม่ใช่ระบบ**ปัดให้อัตโนมัติพร้อมแจ้งเตือน** (เช่น 77 → 75)
- ต้องไม่ต่ำกว่า 35 นาที เพราะ Weight-In + Weight-Out กิน 30 นาทีอยู่แล้ว ต้องเหลือเวลาโหลดอย่างน้อย 1 slot

### ข้อจำกัดของข้อมูลที่ต้องรู้

1. **MAA1-2 กับ MAA3 ใช้ค่าเดียวกัน** — ข้อมูลจริงไม่ได้แยกเกรด MAA1/2/3 ถ้าอนาคตแยกได้ควรมาอัปเดต
2. **NBMA (LORRY)** วัดจาก n-BMA2 เท่านั้น · **n-BMA1/n-BMA2 (Yusen)** รวมกัน — ไม่ได้ยืนยันแยกเกรด
3. **MAA1-2 / MAA3 ที่ 22-24MT** ยังเป็น standard เดิมเพราะ n=0 ไม่ควรค้างไว้ตลอดไป
4. P75 อ่อนไหวกับ n มากกว่าค่ากลาง — กลุ่มที่ n ต่ำสุดคือ MMA1 (ISO Tank) n=44 และ MAA1-2 20-22MT n=38
   ถ้าอนาคตกรองข้อมูลใหม่แล้ว n ลดลงมาก ควรคำนวณ P75 ใหม่
5. ค่าที่แก้อยู่ใน session เท่านั้น ปิดเบราว์เซอร์แล้วหาย — ใช้ปุ่มดาวน์โหลดเก็บไว้

## Business rules ที่ระบบบังคับไว้

**Channel eligibility** (Channel D ไม่อยู่ในระบบนี้ เพราะใช้กับ Truck Drum / Dry Container เท่านั้น)

```
MAA1, MAA2 -> A, C      MMA1   -> C        n-BMA1 -> C
MAA3       -> B         MMA2   -> A, B     n-BMA2 -> C
i-BMA      -> B, C
```

**Standard time — `Transport Co.` เป็นตัวเลือกว่าจะใช้ตารางไหน** (ไม่ใช่ฟิลด์แสดงผลเฉย ๆ อีกต่อไป)
ตารางผลลัพธ์และ hover บน Gantt มีคอลัมน์ **Standard** บอกทุก DO ว่าถูกคิดด้วยตารางไหน

**1) ศรีไทย / SV / VIV → ตาราง LORRY (เหมือนเดิมทุกประการ)**
Weight-In 15 นาที + Load (ตาม product × bracket น้ำหนัก) + Weight-Out 15 นาที
bracket แบ่งจาก Volume: ≤14 → 14MT, ≤22 → 20-22MT, ≤24 → 22-24MT, ≤25 → 24-25MT, มากกว่านั้น → 29MT
บวก **Buffer ของแถวนั้น** (ตั้งในหน้า ⚙️ เวลามาตรฐาน) + Margin เข้าไปในช่วง Load

**2) Yusen → ตาราง ISO Tank** เป็น**เวลารวมทั้งรอบ** (รถถึง Station → ออกจาก Station) และ **ไม่ขึ้นกับขนาดน้ำหนัก**

| Product | Standard (นาที) | | Product | Standard (นาที) |
|---|---|---|---|---|
| i-BMA | 100 | | MMA1 | 110 |
| MAA1 | 110 | | MMA2 | 100 |
| MAA2 | 110 | | n-BMA1 | 100 |
| MAA3 | 110 | | n-BMA2 | 100 |

แตกเข้าโครงเดิม 3 ช่วงเป็น `Weight-In 15 + Load (Standard − 30) + Weight-Out 15`
(คง Weight-In/Out ที่ 15 นาที เพราะขั้นตอนชั่ง/ถ่ายรูป/เอกสารเหมือนกันทุกบริษัทขนส่ง ไม่ขึ้นกับชนิดรถ —
ส่วนที่ต่างจริงคือเวลาโหลดเข้าถัง) → Standard 110 ได้ Load 80 นาที, Standard 100 ได้ Load 70 นาที

**Yusen ตั้ง Buffer = 0** (ตั้งได้รายแถวในหน้า ⚙️ เวลามาตรฐาน แยกจากตาราง LORRY) เพราะ standard ชุดนี้
ตรวจสอบกับข้อมูลจริง 1,213 เที่ยว (ก.ย. 2025 – ก.ย. 2026) แล้วพบว่าอยู่ที่ประมาณ percentile 64–79 ของเวลาจริง
(≈ ระดับ P75 ซึ่งเป็นระดับที่เผื่อไว้สำหรับวางแผนอยู่แล้ว) ถ้าบวกอีก 10 นาทีจะเป็นการเผื่อซ้ำซ้อน ทำให้คิวหลวมเกินจริง
· **Margin รายตัวยังบวกให้ทั้งสองตาราง**

> หมายเหตุจากการวิเคราะห์: i-BMA ที่ Channel B เร็วกว่า Channel C ประมาณ 11 นาที (median 86 vs 97.5, p = 0.0016)
> แต่ standard ที่ได้รับกำหนดเป็นค่าเดียวคือ 100 รอบนี้จึงใช้ 100 ค่าเดียวตามที่กำหนดมา

**ทรัพยากรร่วม (bottleneck จริง)** — กล้อง 1 ตัว + ตาชั่ง 1 จุด ใช้ร่วมกันทั้ง 3 ช่อง รองรับได้ทีละคัน
ระบบโมเดลเป็น **hard constraint**: รถใช้ทรัพยากรนี้ 10 นาที (ตั้งค่าได้) ในช่วงต้นของทั้ง Weight-In และ
Weight-Out ส่วนช่องโหลดยังถูกจองเต็ม 15 + Load + 15 นาทีตามเดิม

## Algorithm

Objective 2 เฟสแบบ lexicographic

1. **Phase 1** — maximize จำนวน DO ยืดหยุ่นที่จัดได้ในวันนั้น
   (DO ที่มี hard deadline เป็นข้อบังคับ `== 1` ต้องถูกจัดเสมอ)
2. **Phase 2** — ในบรรดาคำตอบที่ได้จำนวนเท่ากัน เลือกคำตอบที่เริ่มงานเร็วที่สุดโดยรวม (tie-break อย่างเดียว)

**ทำไมไม่ใช้ greedy** — greedy เวอร์ชันก่อนหน้าปล่อยให้รถชนกันที่กล้อง/ตาชั่งจริง 27 จุดจากการทดสอบ 40 DO
โดยไม่รู้ตัว เพราะไม่ได้ enforce ข้อจำกัดทรัพยากรร่วม MILP พิสูจน์ optimality และบังคับข้อจำกัดนี้ได้แม่นยำ

### การจัดการกรณีที่จัดไม่ได้ (แยก 2 กรณีชัดเจน)

| กรณี | สิ่งที่ระบบทำ |
|---|---|
| DO ยืดหยุ่นเกิน capacity | จัดให้ได้มากที่สุด (optimal) แล้วแสดง DO ที่เหลือในแท็บ "จัดไม่ได้วันนี้" พร้อมเหตุผล — นโยบายคือ **เลื่อนไปวันถัดไป** (ไม่แนะนำให้ย้ายไป Channel D) |
| Hard deadline ชนกันเอง | ไม่เลื่อนเวลาให้เงียบ ๆ แสดง `st.error` พร้อมรายชื่อ DO ที่ขัดแย้ง (หาโดยลอง relax ทีละตัว) แล้วให้ผู้วางแผนตัดสินใจเองว่าจะเปลี่ยนเวลาของ DO ไหน |

### Self-check

ทุกครั้งหลัง solver ตอบ `validate_schedule()` จะตรวจคำตอบซ้ำอีกชั้นก่อนแสดงผล:
ไม่มีรถซ้อนกันในช่องเดียวกัน · ไม่มีรถใช้กล้อง/ตาชั่งพร้อมกัน · ไม่มีงานหลุดนอกเวลาทำงานหรือคร่อมช่วงพัก ·
DO ที่มี hard deadline เริ่มตรงเวลาที่ขอจริง · (ตอน re-plan) คิวที่แช่แข็งยังอยู่ที่เดิม ไม่มีคิวไหนเริ่มก่อนที่รถจะมาถึงได้
และไม่มีคิวไหนถูกจัดย้อนอดีต — ถ้าเจอปัญหาจะขึ้น error สีแดงแทนที่จะแสดงแผนให้ใช้งาน
